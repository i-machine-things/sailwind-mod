# Coding Best Practices & Reminders

> **Style rule:** Notes must be clear and concise — 300 characters or less each. Group by topic, not by date. Whenever a PR review (CodeRabbit or human) catches a mistake, add or amend a note here right away so it isn't repeated.

## General Style Notes

- **Keep lines under 120 characters.** Long lines are hard to review side-by-side in a diff or split editor pane, and tend to signal a line doing too many things at once. Wrap or break up expressions rather than letting them run long.
- **Add docstrings/comments to explain code.** Focus on *why* a function/class exists or *why* it does something non-obvious — the code itself already shows *what* it does. A comment worth writing usually covers intent, assumptions, edge cases, or a gotcha a future reader would otherwise have to rediscover the hard way.

## Proton / Steam

- **BepInEx won't inject under Proton unless Wine is told to prefer the native `winhttp.dll`.** BepInEx's loader hijacks `winhttp.dll` next to the game exe, but Wine's own built-in stub for that name can win over the real file on disk. Fix: add `WINEDLLOVERRIDES="winhttp=n,b" %command%` to Sailwind's Steam launch options. Without it, the game boots fine but `BepInEx/LogOutput.log` never appears.
- **Game install path**: `~/.var/app/com.valvesoftware.Steam/.local/share/Steam/steamapps/common/Sailwind` (Steam AppID `1764530`, Flatpak Steam). Relaunch via `flatpak run com.valvesoftware.Steam steam://rungameid/1764530`.

## BepInEx plugin build (C#/.NET)

- **SDK-style `.csproj` auto-includes `*.cs` files.** Don't also add an explicit `<Compile Include="...">` item for a file already in the project directory — that's `NETSDK1022: Duplicate 'Compile' items`.
- **`net472` target + `Microsoft.NETFramework.ReferenceAssemblies` NuGet package lets `dotnet build` compile a BepInEx 5 plugin on Linux** with no actual .NET Framework (or Mono) installed — it's just reference metadata for compilation, not a runtime.
- **Reference the game's/BepInEx's actual installed DLLs directly (`<Reference><HintPath>`), not NuGet packages, for `Assembly-CSharp`, `BepInEx`, `0Harmony`, and `UnityEngine.*`.** Guarantees the compiled plugin always matches exactly what's loaded at runtime. This is also what the real Sailwind mods on GitHub (`BorderExpander`, `ChaoticWind`) do.
- **`MonoBehaviour`/`BaseUnityPlugin` needs *both* `UnityEngine.dll` (the legacy facade) and `UnityEngine.CoreModule.dll` referenced** — CoreModule alone throws `CS0012` on `MonoBehaviour`. `OnGUI`/`GUI.*` need a further separate reference, `UnityEngine.IMGUIModule.dll`.

## Sailwind modding ecosystem

- **`FloatingOriginManager.instance.GetGlobeCoords(transform)` is the game's real, built-in lat/lon API** — `.x` = longitude, `.z` = latitude, ~9000 Unity units per degree. Confirmed by reading real shipped mod source (`NANDbrew/BorderExpander`, `Rahakami/scrambled-seas`), not by guessing. Don't build a parallel coordinate system — extend this one.
- **`NANDbrew/BorderExpander` already expands `WorldBorder` to ±70° latitude and implements east/west circumnavigation (antimeridian wraparound).** Depend on it rather than reimplementing border/wraparound logic.
- **Installing `BorderExpander`**: not a NuGet/project dependency - it's a separate BepInEx plugin DLL dropped into the live install, same as our own. Get the latest release asset from `gh api repos/NANDbrew/BorderExpander/releases` (`browser_download_url` for `BorderExpander.dll`), verify its sha256 against the release's reported `digest`, place at `BepInEx/plugins/BorderExpander/BorderExpander.dll`. Confirmed GUID (from `strings`-ing the DLL, not guessed): `com.nandbrew.borderexpander`. Its config (`BepInEx/config/com.nandbrew.borderexpander.cfg`, generated on first load) has a `Free Sailing` key under `[Settings]`, default `false` - **must be set `true`** for shifted/real-world coordinates, or vanilla `WorldBorder` bounces you back to the dock on an "out of game area" timer the moment you're outside its hardcoded authored lon/lat box (confirmed live - this is expected behavior reacting correctly to our shift, not a bug, and is exactly why M1 depends on this mod).
- Our own plugin declares `[BepInDependency("com.nandbrew.borderexpander", SoftDependency)]` - confirmed this reorders BepInEx's load log so BorderExpander loads first when both are present (`gh`-sourced live log: `Loading [Border Expander 0.5.0]` before `Loading [Sailwind Real Earth 0.1.0]`, flipped from the no-dependency order). Soft, not hard: we don't call any BorderExpander API yet (its `AddRegion` is there if M2+ needs custom trade-wind regions), so our mod still loads and works - just bounded by vanilla's border - if BorderExpander isn't installed. CodeRabbit (PR #1) flagged that a soft dependency silently allows exactly that stuck-at-border trap - fixed by logging a loud `LogWarning` at startup if `RepositionEnabled` is true but `Chainloader.PluginInfos` doesn't contain BorderExpander's GUID, rather than making it a hard dependency (which would block even just using the overlay/survey features without it).

## Code review / CI workflow

- **`gh pr view <number> --comments` does not show inline review comments** (the kind CodeRabbit posts on specific diff lines) - only general/issue-level comments. Also fetch inline comments with `gh api --paginate repos/{owner}/{repo}/pulls/{number}/comments`, or Rule 0/5's "read all PR comments before proceeding" can silently miss real findings. Caught by CodeRabbit (PR #1) reviewing this exact gap in `CLAUDE.md` itself.
- **CodeRabbit only auto-reviews PRs targeting the repo's default branch.** A PR opened with a different base (e.g. a synthetic root-commit branch, used once here to get a full-history checkpoint review) gets skipped with "Auto reviews are disabled on base/target branches other than the default branch" - trigger it manually with a `@coderabbitai review` PR comment instead.
- **Version-bump counting (`CLAUDE.md` Rule 4) must use `git log ... --format=%s`, not `--oneline`.** `--oneline` prefixes every line with a commit hash, so a "lines starting with `feat:`" count never matches anything against it. Caught by CodeRabbit (PR #1).
- **The pre-commit hook's `_is_git_commit_command` only checked the *first* `git` token in the command.** `shlex.split` doesn't split on `&&`/`;`/`|`, so a chained command like `git add . && git commit -m x` tokenizes as one list with `git` appearing twice - checking only the first occurrence sees `add` next and returns `False`, silently skipping the check on a real commit. Fixed by scanning every `git`-like token (also now matching `git.exe`) and returning `True` if any resolves to `commit`. Caught by CodeRabbit (PR #1).

## Floating origin — don't raw-translate objects far from where they already are

- **Root cause, finally confirmed by instrumenting the engine's own code (not guessed):** `FloatingOriginManager.Update()` auto-triggers the engine's private `Shift()` in a tight `while` loop any time the tracked `shifterObject` (the player)'s **raw** position exceeds `shiftDistance` (confirmed live: **512 units** — tiny). Early attempts physically teleported the player ~290,000 units in one `Transform.position` assignment (far past that threshold), which sent this auto-recentering loop into a runaway: a Harmony diagnostic patch on `Shift()` counted **28,000+ calls in a single frame**, with `outCurrentOffset` ballooning to **10.8 million** (~37x past the intended offset) before reversing direction — an unstable oscillation, not a clean convergence. Confirmed visually too: screenshots during the runaway showed the camera rendering the world as a shrinking planet seen from outside its own skybox (chromatic-aberration rainbow edge, pitch-black unlit ocean), and it ended in an actual process crash (the "EARLY ACCESS" splash screen reappearing afterward meant Unity restarted, not just froze).
- **Earlier theories that were tested and ruled out, in order:** (1) `RealPosToShiftingPos`/`ShiftingPosToRealPos` round-trip not applied — doesn't help, confirmed by decompiling: both are just `pos ± outCurrentOffset`, a no-op before any real shift has ever fired. (2) Crest ocean's own origin-tracking (`FloatingOriginManager.MoveOriginOcean`, called by the real `Shift()`/`NewShift()` before translating anything) not kept in sync — added a reflection call to invoke it ourselves; **did not stop the runaway**, confirmed live (same divergence pattern with or without it). (3) Joint/`connectedBody` anchors on the starter set's mooring springs going stale after a teleport — real and fixed (disable/reassign `connectedBody` around the move), but **not the actual freeze cause** either, since the runaway started before the starter-set patch even ran. Keep all three in mind as real, separate gotchas if raw position-mutation is ever revisited (e.g. for real terrain tiles in M4/M5) — none of them is this bug.
- **The actual fix: stop moving raw positions entirely.** `GetGlobeCoords(obj) = (obj.position - outCurrentOffset - globeOffset) / 9000`. Since this is a pure function of `outCurrentOffset`, setting that one field once (right after `FloatingOriginManager.Start()` resets it to `(0,0,0)`) relabels every object's reported lon/lat uniformly, with **zero** objects ever moved. The player's raw position never leaves the safe zone near origin, so the auto-shift cascade above has no trigger condition to fire. This also incidentally fixes the earlier "phantom dock cleats" bug for free — that was a symptom of physically moving islands away from an unmoved boat/starter set, which can't happen anymore since nothing physically moves.
- **This changes the magnitude-safety story entirely.** The previously "empirically bisected safe range" (comfortable to ~435,000 units, degraded by ~507,000, frozen at ~580,000) was specific to **physically moving objects** and no longer applies to this approach — larger offsets (including the original -64.4/-16.7 Caribbean target) should be safe now, but haven't been empirically retested under the new mechanism yet, so the config default stays conservative (`-32.2/-8.35`) until that's done.
- **New side effect, expected and not a bug:** vanilla `WorldBorder` checks the player's lat/lon against hardcoded authored bounds and triggers "out of game area, recovery in N seconds" once you're shifted outside them, bouncing you back to the dock on timeout. This is exactly why the plan depends on `NANDbrew/BorderExpander` to expand/handle the border for real-world-scale coordinates (see "Sailwind modding ecosystem" above) — not something to patch around here.
- **Diagnostic worth keeping:** a Harmony patch on `FloatingOriginManager.Shift()` that counts/logs calls (throttled) is cheap ongoing insurance — in normal play (and with the offset-only approach above) this should stay near zero; if it ever climbs again, that's the same class of bug recurring.
